# 从 JDK 8 迁移到 JDK 21

## 以 JDK 21 作为公司统一生产基线，保障未来 3–5 年的生态、安全与交付能力

> **核心判断：** JDK 8 仍然“能运行”，但已不再是主流 Java 生态的默认入口。继续停留，将从“主动升级”演变为“被动应急”。

## 为什么现在必须升级

| 维度 | 事实与趋势 | 对公司的影响 |
|---|---|---|
| **Java 生态** | Spring Framework 6、Spring Boot 3 已将 **Java 17 作为最低版本**；Jakarta EE、Quarkus、Micronaut、新版数据库驱动和云 SDK 持续提高最低 JDK 要求。 | JDK 8 无法使用主流框架新版本，框架升级、安全修复和新能力受到限制。 |
| **OpenJDK 社区** | OpenJDK 的语言特性、GC、JVM 优化、诊断能力和 JEP 创新主要集中在 17/21 等新 LTS；工具链和 IDE 也优先适配新版本。 | 社区资源、技术人才和厂商投入逐步远离 JDK 8，问题解决周期和维护成本上升。 |
| **生命周期与安全** | JDK 8 发布于 2014 年，后续支持高度依赖具体厂商和商业合同；JDK 21 是新一代 LTS，具备更清晰、更可规划的维护窗口。 | 降低漏洞修复、合规审计、供应商绑定和紧急迁移风险；越晚升级，兼容性治理成本越高。 |
| **业界与云原生** | 企业新项目、容器基础镜像、云平台和中间件已普遍以 Java 17/21 为主；JDK 21 支持虚拟线程、现代 GC 和更完善的容器适配。 | 提升高并发、弹性伸缩和资源利用效率，统一公司技术栈，降低招聘和运维复杂度。 |

## 不升级的代价

- 产品能力受限：无法及时跟进 Spring、云原生和中间件主流版本。
- 安全与合规风险：依赖旧 JDK、旧框架和旧组件的组合维护。
- 技术债务集中爆发：未来可能在供应商停止支持或安全事件下被迫迁移。
- 人才与效率下降：新员工、工具链和社区最佳实践均以现代 Java 为主。

## 升级后的收益

- 获得主流框架、云平台和工具链的持续支持；
- 建立统一、可持续的 LTS 运行时基线；
- 使用虚拟线程、现代 GC、容器优化等能力；
- 降低安全、合规、运维和长期迁移成本。

## 建议决策

1. 批准 JDK 21 作为公司统一生产基线，新项目禁止新增 JDK 8 依赖。
2. 存量系统分批迁移：先完成依赖盘点和兼容性验证，再按业务优先级推进。
3. 路径：`依赖/代码扫描 → 试点系统 → 核心产品迁移 → 长尾系统收敛`

> **迁移到 JDK 21 不是单纯的版本升级，而是一次生态、供应链、安全和研发效率的基础设施升级。**
